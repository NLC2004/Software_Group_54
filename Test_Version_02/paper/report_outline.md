# TA Recruitment System Report Outline

## 1. 引言

### 1.1 项目背景
- 简述 BUPT International School 助教招聘流程中存在的信息分散、人工管理成本高、角色职责交叉等问题。
- 说明系统希望解决的核心问题：为 TA、MO、Admin 三类用户提供统一的招聘管理平台。

### 1.2 项目目标
- 支持助教岗位发布、浏览、申请、审核、统计与治理。
- 建立清晰的角色权限边界。
- 在课程项目约束下实现一个可演示、可部署、可测试的完整原型。

### 1.3 报告范围
- 说明本报告重点覆盖软件设计策略、架构与模块设计、构建计划、测试策略与技术、生成式人工智能应用。
- 说明报告不展开详细用户手册式页面介绍，只保留少量关键界面作为证据。

## 2. 软件设计策略

### 2.1 设计目标与约束
- 课程项目周期有限，需要优先保证功能完整性、可展示性与可维护性。
- 技术方案需要便于团队成员快速理解和协作，不引入过重的基础设施依赖。

### 2.2 技术选型理由
- 后端采用 Java `HttpServer`，以轻量方式暴露 REST 风格接口。
- 前端采用静态 HTML/CSS/JavaScript，降低开发和部署复杂度。
- 数据层采用 JSON 文件持久化，避免数据库配置成本，便于直接展示数据结构。

### 2.3 关键设计原则
- 角色分离：TA、MO、Admin 的权限和操作范围严格区分。
- 模块化：认证、岗位、申请、草稿、上传、通知、管理等功能按职责拆分。
- 一致性：共享 API 工具层统一处理请求、鉴权和提示反馈。
- 可追踪性：用户故事能够映射到页面、处理器、数据模型和测试用例。

### 2.4 设计权衡
- 说明轻量方案在部署和理解上的优势。
- 说明其在并发能力、扩展性、事务一致性和生产级安全性方面的局限。
- 指出本项目选择“适合课程原型”的工程折中，而非企业级通用方案。

## 3. 系统架构与模块设计

### 3.1 总体架构
- 介绍系统采用的分层客户端-服务端架构。
- 表现层：`TA/`、`MO/`、`admin/` 三个角色门户。
- 服务层：后端处理器接收请求并执行业务规则。
- 持久层：`DataService` 管理 JSON 文件、会话与上传文件。

### 3.2 前端结构设计
- 说明角色页面如何组织。
- 说明 `js/api.js` 如何统一请求封装、token 处理、消息提示和状态显示。
- 强调页面设计围绕角色任务流展开，而非单纯的信息堆叠。

### 3.3 后端模块设计
- `AuthHandler`：登录、注册、资料更新、密码管理。
- `JobHandler`：岗位发布、修改、查询、申请入口。
- `ApplicationHandler`：申请查看、审核、撤回、状态流转。
- `DraftHandler`：申请草稿保存与恢复。
- `UploadHandler`：PDF 简历上传与下载。
- `NotificationHandler`：通知消息管理。
- `AdminHandler`：用户治理、统计、工作量监控、审计、密码重置等。

### 3.4 数据模型与持久化设计
- 说明 `User`、`Job`、`Application`、`ApplicationDraft`、`Notification`、`AuditLog`、`PasswordResetRequest`、`ExportTask` 等核心模型。
- 说明 JSON 持久化如何支撑课程项目原型实现。
- 指出 `data/` 与 `uploads/` 的职责分工。

### 3.5 认证与权限控制
- 说明登录后由服务端签发 token，前端保存在本地并随请求携带。
- 说明不同 handler 中的角色校验逻辑。
- 强调权限控制是三角色系统设计的核心保障。

## 4. 实现与构建计划

### 4.1 增量式实现思路
- 先建立项目骨架：服务器启动、静态资源托管、基础数据读写。
- 再优先打通 TA 的核心申请主流程。
- 然后扩展 MO 审核与岗位管理。
- 最后补充 Admin 治理、统计分析、通知与 AI 匹配等增强功能。

### 4.2 分阶段构建计划
- 阶段一：基础框架与认证功能。
- 阶段二：TA 申请流程与文件上传。
- 阶段三：MO 岗位发布与审核流程。
- 阶段四：Admin 管理、统计和审计功能。
- 阶段五：测试完善、问题修复和界面打磨。

### 4.3 团队协作与代码组织
- 说明团队按角色页面和后端模块分工。
- 说明共享模型与服务层降低了重复实现。
- 说明 Git 如何支持并行开发、版本追踪与回退比较。

### 4.4 可部署性考虑
- 说明项目通过 `build.bat` 和 `run.bat` 即可完成编译与运行。
- 说明轻量技术栈降低了演示和验收环境配置难度。

## 5. 测试策略与测试技术

### 5.1 测试目标
- 验证关键业务流程是否正确。
- 验证角色权限边界是否有效。
- 验证数据持久化、状态流转和异常处理是否符合预期。

### 5.2 测试策略
- 以单元测试和处理器/API 级测试为主。
- 采用角色驱动测试方法，分别模拟 TA、MO、Admin 操作。
- 覆盖正常流程、非法输入、权限越权和边界条件。

### 5.3 测试技术
- 使用 JUnit 5 组织测试。
- 使用 `TestHttpExchange` 模拟 HTTP 请求和响应。
- 使用临时目录隔离测试环境，避免污染正式数据。
- 通过断言检查返回状态码、JSON 内容、文件写入和审计记录。

### 5.4 测试覆盖范围
- 认证与登录注册。
- 岗位创建、编辑、查询与删除。
- 申请提交、撤回、审核、通知联动。
- 草稿保存与恢复。
- 文件上传下载。
- 管理员工作量统计、密码重置和审计日志。
- AI 匹配结果与限额逻辑。

### 5.5 测试结果与局限
- 记录当前自动化测试结果，例如测试总数与通过率。
- 说明当前测试主要覆盖后端逻辑。
- 指出浏览器兼容性、端到端体验、真实邮件与外部 AI API 仍需人工验证。

## 6. 生成式人工智能的应用

### 6.1 在开发过程中的应用
- 用于辅助理解陌生的 Web 开发实现方式。
- 用于定位 bug、提出修复思路和优化代码结构。
- 用于补充页面交互、文案生成和局部实现建议。

### 6.2 在系统功能中的应用
- 介绍 TA 申请流程中的 AI Match Assistant。
- 说明系统如何结合岗位要求、申请文本、用户技能与工作量生成匹配建议。
- 说明 MO 端如何使用 AI 匹配摘要辅助查看候选人。

### 6.3 应用价值与风险
- 价值：提高开发效率、辅助决策、增强系统特色。
- 风险：AI 输出不一定准确，不能替代最终人工审核。
- 控制措施：限制模型选择、限制调用次数、保留人工审批权、通过测试验证接口行为。

## 8. 总结与反思

### 8.1 项目成果总结
- 概括系统已实现三角色招聘管理闭环。
- 强调系统具备可运行、可测试、可展示的课程项目特征。

### 8.2 不足与改进方向
- JSON 存储不适合更大规模并发场景。
- 安全机制、日志治理和异常恢复仍可增强。
- 后续可以引入数据库、成熟框架、端到端测试与更稳定的 AI 服务。
